Chapter 09

Verification

Debut's correctness lives in places a unit test cannot reach: the Accessibility API, a live event tap, real window z-order. The test strategy is therefore layered, and each layer exists because the one below it cannot see something.

The four layers

LayerWhat it provesWhat it cannot see
Unit — swift test --no-parallelModel logic, reconciliation decisions, keyboard interpretation, persistence round-tripsAnything requiring a real window server or another process
Screenshot — ScreenshotTests.swiftSwiftUI actually renders, and geometry matches expectationsWhether the overlay window was ordered in front of anything
E2E in a VM — scripts/tart-e2e.shA real signed app, real permissions, real event tap, real windowsSynthetic drag gestures — virtualized macOS does not deliver them
E2E in the foreground — scripts/e2e-test.shPhysical drag deliveryNothing, but it takes over the developer's desktop

AGENTS.md decides when each layer runs. E2E is for high-risk changes only — global keyboard handling, Accessibility integration, window discovery or lifecycle, stage switching, overlay presentation, persistence reconciliation, app installation, code signing. Routine model, settings, copy, and styling changes use unit and screenshot tests. Running E2E on a copy change is not thoroughness, it is a 10-minute detour.

Unit tests

swift-testing throughout

There is no XCTest anywhere in Tests/. Everything uses @Suite / @Test / #expect from swift-testing. The single string XCTest in the whole repository is in a comment in DiagnosticReporter.swift, explaining why test detection by environment variable does not work under swift-testing (chapter 8). 

TOOLCHAINS=com.apple.dt.toolchain.XcodeDefault /usr/bin/swift test

The TOOLCHAINS prefix is mandatory on this machine — see chapter 10. The 28 test files map roughly one-to-one onto the subsystems in chapters 3–8.

Serialized suites

Three suites are marked .serialized:

  • @Suite("StageController", .serialized) StageControllerTests.swift:151
  • @Suite("Overlay window", .serialized) OverlayWindowTests.swift:5
  • @Suite("Keyboard shortcut customization", .serialized) KeyboardShortcutCustomizationTests.swift:7

All three touch process-global state — real NSWindow instances, the shared DiagnosticReporter, settings on disk. swift-testing runs tests in parallel by default, and these would interfere. If you add a test that creates a window or a controller, it belongs in one of these suites rather than a new parallel one.

Mocks are shipped, not test-only

MockWindowService and MockKeyboardService live in Sources/DebutCore/Services/, not in the test target. They are public types in the library.

Why ship a mock? Because DebutE2E and the benchmark and fixture executables are separate targets that also need them, and a test target's contents are not importable. The cost is a slightly larger library; the benefit is that every harness drives the same seam with the same fake.

MockWindowService Services/MockWindowService.swift:4 is a plain settable-property fake: apps, windowList, untrackableWindowIDList, allWindowIDList (optional, so a test can simulate a failed snapshot rather than an empty one), capturedImages, accessibilityEnabled. It records raisedWindowIDs, activatedBundleID, and captureRequests so a test can assert on ordering and on which windows were asked for.

MockKeyboardService Services/MockKeyboardService.swift:1 is smaller: it holds a weak delegate and exposes simulateEvent(_:) :19, which pushes a DebutKeyEvent straight into the delegate. Every keyboard behaviour in chapter 5 is testable through that one method, without a tap, without permissions, and without stealing the developer's keystrokes.

Tests as an incident record

The reconciler suite is the clearest example of tests-as-documentation. Its test names are not descriptions of methods; they are statements of invariants, most of which exist because something once went wrong:

  • "CG absence never removes a window without a lifecycle event" RuntimeWindowReconcilerTests.swift:83
  • "A window snapshot never substitutes for a termination event" :116
  • "Repeated non-empty partial AX snapshots preserve omitted windows" :176
  • "A later replacement reclaims the retained assignment without a timeout" :332
  • "Dormant recovery does not steal an established assigned window" :542
  • "A replaced Dia window returns to its own stage, not the active stage" :692
  • "Repeated reconciles never drift a settled Dia window between stages" :715
  • "A stale assignment does not strand every other Dia window in the active stage" :741

The last four name a specific application because the bug was found with it. That is deliberate: the reproduction is encoded, not paraphrased. A non-flapping test that runs reconciliation repeatedly and asserts nothing moves is the only way to catch the class of bug where each individual pass looks defensible and the sequence does not.

When fixing a reconciliation bug, write the test at the level of the invariant that was violated, not the line that was wrong. "Does not drift between stages across repeated reconciles" survives a rewrite of the matching tiers; "phase 2 returns index 3" does not.

Screenshot tests

ScreenshotTests Tests/DebutCoreTests/ScreenshotTests.swift:8 is @MainActor and renders real SwiftUI through an NSHostingView into an NSImage, writing disposable PNGs under .build rather than into the source tree: 

static let outputDir: URL = {
    URL(fileURLWithPath: #filePath)
        .deletingLastPathComponent()
        .deletingLastPathComponent()
        .deletingLastPathComponent()
        .appendingPathComponent(".build/test-screenshots")
}()

They are not golden-image comparison tests. Nothing diffs the PNG against a reference. The images are evidence for a human; the assertions are on geometry. Three private helpers extract layout facts from a render:

HelperReturnsUsed for
renderPlateFrames :33[Int: CGRect] keyed by plate indexPlate stack position and scale
renderWindowFrames :44[WindowFrameID: CGRect]Drag-slot anchor stability
renderPlateSurfaceFrames :55[Int: CGRect]The rendered plate surface, distinct from its layout frame

These are what make claims like "Dragging a window preview does not shift the plate stack" :151 and "Window frame preferences remain stable drag-slot anchors" :174 checkable. Both encode the double-layout anchoring trick from chapter 6: the stack's baseline geometry must not move when the visual focus does. A golden-image test would fail on an unrelated colour change and pass on a broken anchor; a frame assertion does the opposite, which is the right way round.

The suite also covers the depth gradient at nine plates, selection state, cross-stage drag growth and surface resizing, and the three onboarding screens — with a MockOnboardingPermissionClient :325 standing in for the real TCC prompts.

End-to-end

The harness

Sources/DebutE2E/main.swift is a ~1,670-line top-level executable, not a test framework. It has a hand-rolled test(_:_:) DebutE2E/main.swift:40 that increments counters and prints ANSI-coloured PASS / FAIL / SKIP lines, and it observes the running app entirely through the diagnostic files: 

func readState() -> [String: String] {
    guard let data = try? Data(contentsOf: diagnosticFile),
          let json = try? JSONSerialization.jsonObject(with: data) as? [String: Any],
          let state = json["state"] as? [String: String]
    else { return [:] }
    return state
}

This is the concrete reason chapter 8's state-provider rule matters. The state block in diagnostic.json is the entire observation channel. There is no IPC, no test hook, no injected harness inside the app — the E2E binary drives the real app with synthetic input and reads a file. An event that does not refresh the state block is, from here, invisible.

The scenarios

They run in ordered groups, each depending on the previous having left the app in a known state:

reachability App is reachable via diagnostics / Event tap is running / Windows discovered desktop surface wallpaper refresh; visible during stage management; yields to Mission Control and App Expose, and returns after each overlay visible; previews contain non-uniform pixels; selection moves and moves back; command hint usage follows real dispatch; overlay closes tab semantics held Tab remains on the last window; a fresh Tab press wraps to first stage mode overlay visible in stage mode; closes after stage commit pointer stationary pointer does not select or magnify; movement enables hover selection; click commits drag window drop across stages; immediate reverse drag; cleanup restores original stages settings a persisted custom shortcut replaces Command-Tab activation; command hints use contextual placements and purpose icons windows forced first launch presents onboarding; relaunch is normal; Settings integrates controls into transparent titlebar chrome

Note "Window previews contain non-uniform captured pixels" :622. That is the AGENTS.md rule about silent capture corruption made executable: a non-nil capture proves nothing, so the assertion is that the image contains more than one distinct luminance value.

Note also the cleanup scenarios — "E2E prepared an empty destination stage without losing source windows" :879, "Window-drop E2E cleanup restores the original stages" :1091, and the two "Debut relaunches normally after …" checks. The suite runs against the developer's or the VM's real session, so it is responsible for putting the session back.

The drag skip

Two scenarios are named in a set at the top of the file :16: 

let hostedDragTests: Set<String> = [
    "Dropping a window updates the source and destination stage models",
    "The refreshed destination plate supports an immediate reverse drag",
]

They are skipped when GITHUB_ACTIONS=true or DEBUT_SKIP_VIRTUALIZED_DRAGS=1 :13-15, and the skip prints an explanation that differs by environment: GitHub-hosted macOS "does not deliver synthetic drag gestures; run this check locally", versus virtualized macOS "use Tart run-all to diagnose" :34-37.

These are skips, not deletions, and the distinction is the point. A deleted test is an invariant that no longer exists. A skipped test with a printed reason is an invariant that this environment cannot check — the count still appears in the summary line ("N/M passed, K skipped, F failed" :1237), so the gap stays visible. The drag loops also collapse to zero iterations under the skip flag :953, :1030, so no time is spent moving a pointer that nothing will observe.

Running E2E

Tart, first choice

brew install cirruslabs/cli/tart
./scripts/tart-e2e.sh prepare   # one time; clones and sizes the VM
./scripts/tart-e2e.sh run       # the normal loop
./scripts/tart-e2e.sh run-all   # diagnose the drag skips only
./scripts/tart-e2e.sh status
./scripts/tart-e2e.sh stop

prepare clones the Tahoe base image and sets it to 6 CPUs, 8 GB, and a 1440×900 display scripts/tart-e2e.sh:50. The VM is started with every host input path detached: 

tart run --no-graphics --no-audio --no-clipboard --no-pointer --no-keyboard \
         --dir="$SHARE_DIR" "$VM_NAME"

That is what makes it safe to run while working: synthetic keystrokes and pointer moves stay inside the guest. Building stays on the host for fast incremental iteration — only compressed, cache-busted Debut.app and DebutE2E artefacts cross the shared directory (default ~/Library/Caches/Debut/TartE2E). Xcode is deliberately not installed in the guest. Later runs reuse the warm VM and its GUI session, which is the difference between a 30-second loop and a boot.

The script's own output is the authority on how many scenarios pass. Do not encode a pass count in your head or in a commit message — the skip set changes with the environment.

Permissions inside the guest

A guest cannot click "Allow" in a TCC dialog, so scripts/tart-e2e-guest.sh writes the grants directly. For each of kTCCServiceAccessibility, kTCCServiceScreenCapture and kTCCServicePostEvent, it extracts the app's designated requirement from codesign -d -r- tart-e2e-guest.sh:55, converts it to the binary csreq blob TCC stores, and INSERT OR REPLACEs a row into the system TCC database at /Library/Application Support/com.apple.TCC/TCC.db — and, for the two user-scoped services, into the per-user database as well.

This works only because SIP is off in the guest and the app is signed with a stable self-signed certificate, so the csreq continues to match across rebuilds. The script refuses to run outside the guest :22, since it replaces /Applications/Debut.app and rewrites TCC.

GitHub-hosted, fallback

.github/workflows/e2e.yml runs on macos-26 and does three things: verify the workflow contract, run ./scripts/ci-e2e.sh, and upload evidence as an artefact even on failure. Use it when Tart is unavailable or as remote confirmation — not as a routine trigger.

Foreground, last resort

./scripts/e2e-test.sh is the only local way to exercise physical drag delivery. It displays the overlay, injects global keyboard and mouse events, and captures the live desktop. Warn the user before running it, and only when the drag scenarios are material to the change.

The shell contract suite runs before the unit suite it validates. Documentation drift about how to run E2E is itself a failure condition here, which is unusual and worth respecting when editing those files.

The workflow AGENTS.md mandates

For completeness, since it governs every change in this repository:

  1. Work in a clean, isolated git worktree — never the primary checkout. One task per worktree.
  2. Write or update the tests first. Run them. Confirm they fail for the expected reason — a test that passes before the fix proves nothing.
  3. Implement, then run until green.
  4. Run the relevant unit and screenshot tests; run E2E only if the change is high-risk.
  5. Commit with the Linear issue ID as a prefix, merge to main, remove the worktree and branch.
  6. Build, install to /Applications/Debut.app, push main.

Step 6 is not optional bookkeeping: the installed app must always match the source. A stale /Applications/Debut.app makes every subsequent manual observation untrustworthy, and E2E runs against the installed bundle.
