Chapter 07

Persistence and reconciliation

Writing state to disk is the easy half. The hard half is recognising, on the next launch, that a window with a new numeric ID and possibly a different title is the same window you saw yesterday — and refusing to guess when you cannot tell.

What is on disk

Everything lives in ~/Library/Application Support/Debut/:

FileContentsWritten by
state.jsonThe encoded SpaceManager: spaces, their order, window assignments, dormant assignments, active space IDDebounced on mutation; flushed on terminate
settings.jsonThe encoded AppSettings: appearance, bindings, exclusions, delays, hint countsImmediately on any settings change
diagnostic.jsonLive snapshot: state block, recent events, performance, presentation tracesChapter 8
diagnostic.jsonl (+ .1)Append-only lifecycle event log with one rotated generationChapter 8

Both JSON files are encoded with [.prettyPrinted, .sortedKeys] and written with options: .atomic, so a crash mid-write cannot leave a truncated file. Sorted keys make a diff between two state files readable, which matters more than it sounds when debugging assignment churn.

StateStore Services/StateStore.swift:3 is Sendable and takes its directory by injection, with a convenience initialiser resolving the real path. Every save is wrapped in a statePersistence performance span, which is one of the three operations gated by a budget.

Asymmetric error handling

load() returns a fresh empty SpaceManager if the file is missing or if decoding fails — deliberately, and with a comment recalling a legacy format where spaces held applications rather than windows. A user with an unreadable state file gets a working app with a lost layout, not a launch failure.

loadSettings() by contrast rethrows. Every call site wraps it in try? anyway, so the observable behaviour is the same; the difference is that the store does not pretend to know what a settings failure means.

The debounced saver

DebouncedSaver Services/DebouncedSaver.swift is thirty lines: a serial queue, one DispatchWorkItem, and a 0.5 second delay. scheduleSave cancels the outstanding item and re-arms. flushNow cancels and performs a synchronous save on the queue — that synchronous barrier is what makes applicationWillTerminate a sufficient save point.

It coalesces whole SpaceManager values, not deltas, so a save always writes the latest snapshot handed to it. Dropping intermediate states is the entire point.

Schema evolution

There is no migration framework and no schema version number. Compatibility is handled per model, in hand-written decoders, according to one rule: fields present since the beginning are required; everything added later is optional with a default. 

// SpaceManager.init(from:)
spaces                   = try decode(...)                    // required
activeSpaceID            = try decode(...)                    // required
dormantWindowAssignments = try decodeIfPresent(...) ?? []     // added later

// then: drop any dormant assignment whose spaceID no longer exists

Models/SpaceManager.swift:32

AppSettings.init(from:) follows the same shape across a long list of later additions — telemetry opt-in, presentation delay, key bindings, both quick-switch modifier sets, preview policy and TTL, hint visibility, usage counts.

Unknown keys are simply ignored by JSONDecoder, which is what made removing Space.name and the default-space-name setting safe without touching anyone's existing files: the leftover keys are read and discarded. Key bindings go further — the decoder drops unrecognised action names and merges what remains over the shipped defaults, so a file from an older build gains new actions and loses retired ones automatically.

Adding a field

Add the property with a default, add one decodeIfPresent … ?? default line to the hand-written initialiser, and encode it. Do not add it as a required key: every existing installation's file predates it.

Reconciliation

RuntimeWindowReconciler Services/RuntimeWindowReconciler.swift is the most intricate algorithm in the codebase. It runs at startup and again on every application activation, and its job is to answer: given the assignments I remember and the windows that exist right now, which are the same windows?

It is a struct with one piece of carried state, provisionalWindowIDs, so AppDelegate keeps a single long-lived instance across activations. Provisional means "I placed this window somewhere, but I am prepared to be told otherwise" — see phase 3.

Phase 1 — replacement recovery

Only runs if the all-window-IDs snapshot succeeded (a nil snapshot proves nothing, per chapter 3). It collects assignments whose window ID is no longer present in the window server's list, then matches them against live windows in two tiers:

TierRuleReason code
A — exact Same bundle ID and same title, restricted to live windows that are currently unassigned or provisional recoveredExact
B — bundle-only After removing tier-A consumptions, for each bundle: only if the remaining assignments and the remaining unassigned live windows form a complete one-to-one set, zip them positionally recoveredBundle
Use it only when all remaining assignments and unassigned live windows for that bundle form a complete one-to-one set, avoiding arbitrary partial reassignment. RuntimeWindowReconciler.swift:317

That completeness condition is the whole safety argument for tier B. Three saved assignments and three live windows for one bundle: the pairing may be wrong in detail, but every window ends up in a space that genuinely belonged to that application. Three saved and one live: refuse, because any pairing is a coin flip that could drag a window into the wrong project. Bundles are iterated in sorted order so the outcome is deterministic.

A match rewrites the assignment's IDs in place, preserving both the space and the MRU index.

Phase 2 — dormant restoration

The same two-tier matcher runs again, this time over the dormant assignments, sorted by (space index, window index) so restoration order is stable. Each restored window is reinserted at its recorded index within its space rather than appended, so a relaunched app comes back in the same order it left.

Phase 3 — additions

Live windows that matched nothing and are assigned nowhere have to go somewhere. The default is the target space — the active one at startup. But before that, the reconciler looks for a stranded space: if exactly one space still holds an unrecovered assignment for that bundle, the new window goes there instead.

spread across several, choosing one would be the same guess zip already makes. RuntimeWindowReconciler.swift:267

When a bundle has stranded or dormant assignments, the newly placed window is also marked provisional, so a later reconcile — once the app finishes opening its remaining windows — may legitimately steal it back into a better match. Rebinding a provisional window removes it from all spaces first, so it can never end up assigned twice.

What is never done

Unmatched assignments are not removed

A live assignment whose window ID is absent from the window server's list stays exactly where it is:

CG absence is evidence that an ID may have been replaced, never evidence that a window was destroyed. Only AX lifecycle events remove assignments. RuntimeWindowReconciler.swift:116

Unmatched dormant assignments likewise just stay dormant. There is no expiry sweep, no "clean up old entries" pass, and adding one would be a bug.

Reason codes

Every placement decision records why it happened — recoveredExact, recoveredBundle, dormantRestored, strandedSpaceRecovered, new. These reach the diagnostic log, and they are how a misplacement is diagnosed afterwards. A window that reappears as reason: new when it should have been recovered is the signature of the class of bug this whole module exists to prevent.

The incident encoded as tests

Four tests in RuntimeWindowReconcilerTests.swift (:692, :715, :741, :766) build the same fixture from a real incident, with real window IDs and titles, including a window annotated "closed without a destroy notification; no live window will ever match". They are the most readable specification of the stranded-space and provisional machinery that exists. One of them asserts the reconciler does not flap: repeated identical snapshots must converge, not oscillate.

Startup, end to end

load state.json ──► SpaceManager (or a fresh one on failure) │ ▼ apply exclusion list excluded bundles are removed outright │ ▼ reconcile against live windows ◄── phases 1–3 above │ (skipped entirely if the live list is │ empty while apps and assignments exist) ▼ removeEmptySpaces() keeps spaces holding dormant assignments │ ▼ populate a default space ONLY if every space is empty AND there are │ no dormant assignments (there is always >=1 space) ▼ choose the starting space the one owning the currently focused window, │ else the first ▼ activate it the first real space switch of the session

Dormancy, in code

A DormantWindowAssignment is a SpaceWindow plus the spaceID and windowIndex to return to. The lifecycle:

EventEffect
Process exits (kernel source, or workspace notification as backup)Its windows leave the live space view and become dormant assignments at their current positions
Window reports an untrackable Accessibility classificationSame — dormant, never deleted
App launches againPhase 2 restores by exact match, then by complete one-to-one bundle match
kAXUIElementDestroyedNotificationThe assignment is genuinely removed
App is excluded, or the cache is resetPurged
Containing space is deletedPurged — and on decode, any dormant assignment pointing at a missing space is pruned as a safety net
Time passesNothing. There is no expiry.

Other persisted state

Two things live outside the store. Onboarding completion is a UserDefaults flag, with a migration that reads the legacy "has launched before" key so upgrading users are not shown a first-run screen. The telemetry queue and its daily quota are separate files with their own bounded formats — see chapter 8.

Diagnosing persistence problems

  1. Read state.json. Sorted keys make it diffable; the space array order is the label order.
  2. Grep diagnostic.jsonl for reason codes. A cluster of reason: new after a restart means recovery failed, not that windows were created.
  3. Check for windows_reconcile_skipped — the empty-snapshot bailout fired, and the state you are looking at is untouched rather than wrong.
  4. Export a diagnostic snapshot from Settings. It embeds both files plus the live tracking tables, which is the only way to see armed-versus-known divergence.
