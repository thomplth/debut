Chapter 05

Keyboard and the event tap

Debut intercepts the system's own switcher shortcuts before any application sees them. That is done with a single CGEventTap, and almost every design decision in this layer follows from one fact: a tap that is slow is a tap the system turns off.

Creating the tap

EventTapKeyboardService Services/EventTapKeyboardService.swift:3 conforms to KeyboardService and ShortcutRecordingService, is @unchecked Sendable, and guards its mutable configuration with two separate NSLocks — one for tap lifecycle, one for bindings and cached state. Splitting them means a settings change cannot contend with a tap start/stop.

start(delegate:) EventTapKeyboardService.swift:86 spawns a dedicated Thread named com.thomplth.Debut.event-tap and blocks on a semaphore for up to two seconds waiting for it to come up. It returns a Bool, so a tap that could not be created — the normal outcome when Accessibility permission is missing — surfaces as false rather than as silence. The controller reports that as event_tap_created or event_tap_failed, and both eventTapRunning and eventTapStarted appear in the diagnostic state block.

On that thread:

let mask = keyDown | keyUp | flagsChanged

CGEvent.tapCreate(
    tap: .cgSessionEventTap,       // session-wide, all apps
    place: .headInsertEventTap,    // before anyone else in the chain
    options: .defaultTap,          // active: we may modify or swallow events
    eventsOfInterest: mask,
    callback: eventTapCallback,    // a file-private C function
    userInfo: Unmanaged.passUnretained(self).toOpaque()
)

EventTapKeyboardService.swift:110

The callback is a free function; it recovers self with Unmanaged<EventTapKeyboardService>.fromOpaque(userInfo).takeUnretainedValue(). The run-loop source is added to this thread's run loop in .commonModes, the tap is enabled, and CFRunLoopRun() blocks; everything after that call is teardown. stop() disables the tap, stops the run loop, and wakes it.

Unretained refcon

passUnretained means the service must outlive the tap, and nothing in the type system enforces that. In practice AppDelegate holds it for the process lifetime.

Re-enabling after the system disables it

macOS disables a tap that takes too long, and reports it as a .tapDisabledByTimeout or .tapDisabledByUserInput event. The callback intercepts both before any Swift dispatch happens, calls reenableEventTap(), and passes the event through. There is no watchdog timer; this is the only re-arming path.

Never blocking

The production callback sets deliverAsynchronously: true, so delivery hops to the main queue and the callback returns immediately. A separate synchronous entry point exists purely as a test seam. A test asserts that the tap does not run on the main thread, so that "just make it main-actor" cannot be reintroduced accidentally.

The decision tree

handleCGEvent(type:event:deliverAsynchronously:) EventTapKeyboardService.swift:188 is the whole policy. The order is load-bearing at almost every step; reordering it is the single easiest way to break Debut subtly.

0. open a performance span (closed by defer); read keyCode + flags once 1. shortcut-recording keyUp drain ................... consume 2. shortcut-recording keyDown ....................... consume (highest priority: steals ANY combination, including Cmd+Tab, while a shortcut is being recorded in Settings; Escape cancels) 3. quick-switch keyUp drain ......................... consume (even if the modifier was already released) 4. modifier-free session commit ..................... consume (a binding with no modifier ends its session when the trigger key is released) 5. .flagsChanged .................................... session modifier no longer held -> end session, emit .cmdRelease, consume otherwise -> pass through 6. QUICK SWITCH ..................................... consume checked BEFORE the configured-binding table and BEFORE session tracking 7. configured GLOBAL action ......................... overlay activation -> begin session, open a presentation trace, consume same-app cycling -> only while the overlay is hidden, consume 8. guard stageManagerActive else ................... pass through 9. guard overlayVisible else ................... pass through (session alive but overlay closed after Escape: only the global activation shortcuts in step 7 can reopen it) 10. Cmd+Q escape hatch .............................. pass through unless the user has explicitly bound that combination 11. overlay is visible: keyUp -> consume keyDown -> dispatch the session action, then ALWAYS consume

Several of those steps deserve their reasons spelled out.

Why quick switch is tested before everything else

Quick-switch chords must work with no session active, and they must not be reachable through the ordinary binding table. Step 7 explicitly refuses to dispatch any action that carries a quick-switch position — only step 6 can fire those. The test "Legacy per-number bindings cannot move quick switch away from digit keys" KeyboardShortcutCustomizationTests.swift:128 pins that.

A rule that no longer needs a step

AGENTS.md instructs you to "check the Option flag BEFORE bare Tab", so that Cmd+Option+Tab is not swallowed by the Cmd+Tab handler. No such branch exists in the current code, and none is needed: binding lookup is exact KeyCombo equality across all four modifier booleans EventTapKeyboardService.swift:408, Models/KeyBinding.swift:398, so a combo with Option set can never match the bare-Tab binding in the first place. The rule describes an ordering hazard that the data model has since made unrepresentable. Preserve the exact-equality matching and the hazard stays gone.

Why everything is consumed while the overlay is visible

Both keyDown and keyUp return nil. Passing keyUp through leaks into the active application: you would navigate the overlay and simultaneously type into whatever is behind it. The comment is blunt — "Always consume — never let keyboard events leak to the active app."

Why Cmd+Q survives

Keep the standard app-quit shortcut available unless the user explicitly assigns that physical key combination to a Stage Manager command. EventTapKeyboardService.swift:348

The session state machine

Three fields hold the whole thing: stageManagerActive, sessionPrimaryModifier, and sessionTriggerKeyCode. They are deliberately not lock-protected, because only the tap thread ever touches them.

beginSession(using:) is idempotent. It derives the modifier to watch from the binding, in priority order command → control → option → shift; a binding with no modifier at all stores the trigger key code instead. While a session is running, lookups subtract the session modifier from the incoming flags before matching — which is how a binding recorded as plain "Tab" resolves while Cmd is physically held down.

There is no tap-versus-hold timer in the tap

This surprises everyone. The tap always begins a session and always opens the logical overlay; the presentation is what is deferred, by the configurable delay (default 80 ms), guarded by a monotonically increasing generation counter. Releasing the modifier before the deadline bumps that generation and dismisses the pending presentation with the outcome releasedBeforePresentation — the window switch happens, the overlay simply never appears. A cmdTabTap event type does exist in the enum, but only the mock keyboard service ever emits it.

Overlay visibility is a separately locked mirror pushed in by the controller. Escape closes the overlay and restores the pre-overlay stage but leaves stageManagerActive true — the session continues until the modifier is released, and same-app cycling stays stage-isolated because it is intercepted at step 7, above the overlay gate.

Quick switch

Two independently configurable modifier sets — direct stage switching (default Control) and same-app switching (default Control+Option) — are both evaluated on every keyDown by quickSwitchStagePosition(keyCode:flags:modifiers:) EventTapKeyboardService.swift:460.

The match is exact equality after masking to the four modifier flags, so Ctrl+Shift+1 does not fire Ctrl+1. The event becomes the same-app variant whenever the same-app set matched EventTapKeyboardService.swift:282 — the same-app chord wins outright if both sets somehow match, and the stage position is then taken from whichever set produced one. Digits map explicitly from 1 to 9; 0 falls through to the default case and there is no action for it. Repeat presses are swallowed by an insert-if-new set, so holding the chord neither re-dispatches nor leaks.

Exclusions are the reason the cached bundle ID exists: 

// paraphrased; the real guard also requires a non-empty set and a non-nil cached ID
if !excluded.isEmpty, let bundleID = cachedFrontmostBundleID, excluded.contains(bundleID) {
    return event   // let the app keep its own Ctrl+digit shortcuts
}

The cache is fed from workspace activation notifications. Asking NSWorkspace for the frontmost app inside the callback would be a cross-process query on the input path — exactly the thing that gets a tap disabled. All four configuration values are read in a single locked tuple to minimise time under the lock.

Actions and bindings

KeyAction Models/KeyBinding.swift:3 is a string-backed CaseIterable enum in four groups:

GroupScopeCases
Activationglobal activateNextWindow, activatePreviousWindow, activateNextStage, activatePreviousStage, activatePreviousStageAlternate
Quick switchglobal quickSwitchStage1 … quickSwitchStage9
Same-app cyclingglobal nextAppWindow, previousAppWindow
Sessionsession nextWindow, previousWindow, previousWindowAlternate, nextStage, previousStage, jumpToStage1…9, moveWindowUp/Down, moveWindowLeft/Right, dismissOverlay

Derived properties on the enum carry the semantics the raw cases cannot: shortcutScope, isOverlayActivation, quickSwitchPosition, isSameAppCycle, and toKeyEvent(). Alternates collapse in toKeyEvent() — previousWindowAlternate becomes previousWindow and jumpToStage9 becomes jumpToLastStage, because the ninth slot targets the last stage rather than literally stage 9.

A KeyCombo is a key code plus four booleans, not raw CGEventFlags. Its decoder defaults every missing modifier to false, which is one half of the forward-compatibility story; the other half is in KeyBindings.init(from:), which decodes an alternating key/value container, silently drops unknown action strings, and then merges the result over the shipped defaults. The consequence is worth stating plainly:

Binding schema evolution

A settings file written by an older build gains defaults for actions added since, and loses actions that were retired, without any migration code. Two tests pin both directions.

Lookup is scope-qualified — action(for:scope:) iterates allCases, which makes match order deterministic and lets the same physical combination mean one thing globally and another inside a session.

Recording a shortcut

ShortcutRecorderView Views/ShortcutRecorderView.swift records through the tap itself (step 2 of the decision tree) as well as through a normal keyDown, so it can capture combinations the system would otherwise eat. Pure modifier key codes are ignored, and Escape cancels.

On capture, ConflictDetector Models/ShortcutConflict.swift:25 produces one of three conflict kinds:

.internal
Another Debut action in the same scope already uses the combination. Resolving it removes the other action's binding entirely, leaving it unbound.
.system
Advisory only, for the well-known system combinations, and only for global-scope bindings.
.requirement
A global binding with no modifiers would intercept ordinary typing.

Command hints

Hints annotate the overlay with the commands available at that moment, and retire themselves as you learn them. 

.automatic -> shown while usageCount <= 3
.never     -> never shown
.always    -> always shown

The counter stops incrementing at 4. The comment — "Records only the four uses needed by automatic mode. Returns whether state changed" — captures both reasons: counts cannot grow unbounded, and once saturated the settings write is skipped entirely, so a heavily used command costs nothing on the input path.

The pipeline is: the key event exposes a commandHintAction (nil for repeats, modifier release, quick switch, escape, and same-app cycling KeyboardService.swift:63) → the controller's onCommandUsed closure → the delegate records usage, reports command_hint_usage_observed, and re-renders if the overlay is open. The catalogue groups hints into three placements and drops a whole group only when every action in it has retired.

Input latency

InputLatencyClock Services/InputLatencyClock.swift measures the gap between the timestamp on the CGEvent and its arrival in the tap. The implementation looks paranoid until you read the comment:

CGEventTimestamp is documented as "roughly, nanoseconds since startup", but Apple Silicon's mach timebase is 125/3, so a raw tick reading and a nanosecond reading of the same field differ by ~41×. Rather than trust the header, accept whichever unit puts the event within a plausible window. InputLatencyClock.swift:30

So it evaluates both interpretations, discards negatives and anything beyond a two-second plausibility limit, and takes the smaller. A keypress cannot have waited weeks, so the wrong interpretation discards itself.

Notes for anyone modifying this file

  • The tap passes a zero configured delay when it opens a presentation trace; the controller back-fills the real value. The tap deliberately knows nothing about settings-owned timing.
  • The tap retro-links its already-open span to the new trace ID, so a single trace spans recognition through main-actor dequeue. See chapter 8.
  • Session fields and the quick-switch key set are unguarded by design. Touching them from anywhere but the tap thread is a data race, not a style issue.
  • There is an unscoped action(for:) that uses first(where:) over a dictionary and is therefore order-nondeterministic. It is used only when evicting a conflicting binding, never on the input path. Do not reach for it elsewhere.
