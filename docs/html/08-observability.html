Chapter 08

Observability: diagnostics, performance, telemetry

Debut runs in the background, reacts to keystrokes in single-digit milliseconds, and manipulates windows it does not own. Almost none of that is observable by looking at the screen. This chapter covers the three separate instrumentation systems that make it observable instead — and the incidents that shaped each of them.

The three systems have genuinely different jobs, and conflating them is the easiest way to misread the code:

SystemQuestion it answersWhere it goes
Diagnostics
DiagnosticReporter		What happened, in what order, and what is the session's state right now?diagnostic.json, diagnostic.jsonl on this machine
Performance
PerformanceRecorder		How long did that take, and did the process burn CPU or block?os_signpost + in-memory buffers, surfaced in the snapshot
Telemetry
TelemetryExporter		Is this slow for other people too?Off the machine — but only if credentials are configured, which they are not in the stock build

Diagnostics

Two levels, one of which survives a restart

Every reported event is tagged with a DiagnosticLevel Services/DiagnosticReporter.swift:5, and the doc comment states the whole design rule:

Controls whether an event survives a restart. Input and hover events fire dozens of times per second, so only lifecycle events earn durable storage. DiagnosticReporter.swift:3

So .lifecycle events (stage switches, window discovery, reconciliation, app launches and exits, assignment changes) append to the durable log. .transient events (a held Tab stepping the selection, pointer hover, per-frame work) land in the in-memory ring and the live snapshot only. Both levels refresh the state block — see the warning below for why that matters.

Three files

FileShapeLifetime
diagnostic.jsonSingle JSON object: state block, recent events, performance snapshot, overlayPresentation tracesOverwritten on every report — always describes now
diagnostic.jsonlOne JSON object per line, append-onlyGrows until rotation
diagnostic.jsonl.1SameExactly one previous generation; older data is gone

Rotation is size-triggered and deliberately primitive (rotateIfNeeded(incomingByteCount:) DiagnosticReporter.swift:225): if the current file plus the incoming line would exceed rotationByteLimit (default 2_000_000 :67), delete .jsonl.1, move .jsonl onto it, and start fresh. There is no compression and no third generation. The cap on retained history is therefore between 2 MB and 4 MB, which for lifecycle-only events is a long session.

Writes go through a serial DispatchQueue labelled com.thomplth.Debut.diagnostic. Appends use a FileHandle seeking to end-of-file; only the very first write of a generation uses write(to:options:.atomic). A shared ISO8601DateFormatter is held as nonisolated(unsafe) and touched only on that queue, with the reason spelled out in place:

Allocating a formatter per event is measurable on the input path. Only touched on queue, which serializes the access the type itself does not guarantee. DiagnosticReporter.swift:43

The bundle-identifier gate

DiagnosticReporter.shared is a singleton, and test suites that exercise StageController report through it. If those reports landed in the real Application Support directory they would pollute the log that a live session is diagnosed from. So the default directory branches on a positive identification of the shipped app DiagnosticReporter.swift:32-34: 

private static var isHostedByDebutApp: Bool {
    Bundle.main.bundleIdentifier == "com.thomplth.Debut"
}

When false, diagnostics are written to $TMPDIR/DebutDiagnostics-<pid>/ instead. The comment explains why it is not written as a test-detection check:

Identifies the shipped app positively. Test runners expose neither an .xctest bundle nor XCTestConfigurationFilePath under swift-testing, so detecting them by absence is unreliable. DiagnosticReporter.swift:29-31

PerformanceRecorder uses the same gate for a different reason — see the resource reader below. If you ever change the bundle identifier, both of these silently flip behaviour.

The state provider, and the stall it caused

The state block in diagnostic.json is produced by a closure registered with setStateProvider(_:runsOnMainQueue:) DiagnosticReporter.swift:122. It is the only mechanism by which the E2E suite can observe a running session, so the contract around it is load-bearing.

The naive implementation — call the provider synchronously at report time — is wrong when the reporter is invoked off the main thread and the provider reads main-queue-owned state. Hopping to main and waiting charges the caller for whatever unrelated work main is already doing. That produced a memorable false diagnosis:

Waiting on the main queue here charged the caller for unrelated main work: a 3.1s overlay render stall was billed to a preview capture that had not started. Hand the refresh to main and use the last snapshot. DiagnosticReporter.swift:157-159

So currentState() :162 does this instead:

  • If the provider does not need the main queue, or we are already on it, call it directly and publish the result.
  • Otherwise, schedule a coalesced refresh on main and return publishedState — the last known good snapshot.

The refresh writes its own snapshot file when it completes, otherwise the state block would stay one report behind forever for any code path that only reports off the main thread. The scheduling flag is guarded by an NSLock that is deliberately separate from the write queue, so reading state never waits behind pending file I/O.

Every reported event must refresh the state block — including .transient ones. Long stretches of an E2E scenario (a held Tab, for example) emit nothing but transient events. If those skip the state provider, the block goes stale, E2E assertions read yesterday's truth, and unit tests stay green the whole time. This is the failure mode that AGENTS.md calls out explicitly.

flush() :144 is just queue.sync {} — a barrier that gives tests a deterministic point at which the files on disk reflect every reported event.

Exporting a bundle

DiagnosticExporter Services/DiagnosticExporter.swift:134 produces a single self-contained JSON file (named Debut-Diagnostics-yyyy-MM-dd-HHmmss.json AppDelegate.swift:918) containing:

  • the parsed contents of state.json and settings.json;
  • both lifecycle log generations, parsed line by line;
  • a runtime object: every window with owner, title, and frame; running apps; screens; and the WindowTrackingDiagnosticSnapshot of armed-versus-known window IDs;
  • metadata: app version, OS version, permission states.

Note the privacy inversion. The local export deliberately includes window titles DiagnosticExporter.swift:215, because a reconciliation bug is unreadable without them. Telemetry, which leaves the machine, has no field capable of carrying one. The two systems point in opposite directions on purpose: maximum detail locally, structurally-enforced minimum remotely.

Recording a span

PerformanceRecorder PerformanceObservability.swift:250 is an @unchecked Sendable class behind an NSLock, not an actor — spans begin and end on whichever thread does the work, including the event tap thread, and an actor hop there is exactly what must not happen.

begin(_:workload:) :292 returns a correlation UUID, emits an os_signpost interval begin on subsystem com.thomplth.Debut / category performance, and samples the process resource counters. end(_:) :319 computes the duration, the resource delta, appends to a PerformanceSampleBuffer (which retains percentiles :86) and a bounded recent-observations list, and hands the observation to the registered handler. cancel(_:) :395 drops a span without recording, which is what an aborted presentation uses.

Two mutators exist because facts about a span arrive after it starts: updateWorkload(_:for:) (the window count is not known until discovery completes) and updateTraceID(_:for:) (which stitches a span into an overlay presentation trace).

Why resourceDelta is per-span and never process-wide:

Measured across this span alone. A process-wide delta shared between operations is overwritten by whichever one ends last, which makes it unusable as evidence about any of them. PerformanceObservability.swift:229-231

The resource reader

SystemProcessResourceReader :180 reads proc_pid_rusage(getpid(), RUSAGE_INFO_V4, …) for CPU time, physical footprint, wakeups, disk bytes and page-ins, then calls task_threads for the live thread count — carefully vm_deallocate-ing the returned array, which is a Mach allocation the caller owns.

That is not free, and it runs on the boundary of every span. Hence the same bundle gate as diagnostics :266:

Unit and screenshot suites create many controllers concurrently. They test injected readers separately and must not turn every synthetic operation into a Mach task scan. PerformanceObservability.swift:264-265

Outside the shipped app, UnavailableProcessResourceReader returns nil and every resourceDelta is absent. Tests that care inject a real or fake reader explicitly.

Overlay presentation traces

Timing the overlay as one number tells you it was slow and nothing else. So OverlayPresentationRecorder Services/OverlayPresentationRecorder.swift records a trace of 14 named phases :11, in causal order:

activation_recognized keystroke classified in the tap callback main_actor_dequeued handoff to main completed fullscreen_probe_completed is a fullscreen Space in the way? controller_accepted StageController agreed to present presentation_scheduled deferred presentation armed presentation_deadline_fired preparation_began preparation_completed view model built window_ordered NSWindow ordered front render_submitted SwiftUI submitted a frame reveal_completed user can see it first_preview_completed asynchronous, after reveal all_previews_completed asynchronous, after reveal wallpaper_completed asynchronous, after reveal

The last four intentionally land after the overlay is already visible; the overlay does not wait for its own thumbnails. Each trace also carries an outcome :28 — presented, released_before_presentation, fullscreen_rejected, superseded, hidden_before_reveal, app_terminated — so an abandoned presentation is distinguishable from a slow one rather than just vanishing.

Context enums accompany each trace and exist to answer "why was this one slow": OverlayProcessUse (first attempt vs later), OverlayPreviewCacheState (empty / partial / complete), OverlayWallpaperState, OverlayHostingViewState (created / reused — see chapter 6) and OverlayProcessAge. A trace ID is propagated into PerformanceRecorder spans via updateTraceID, so a signpost interval and a presentation phase can be correlated after the fact.

Budgets

PerformanceBudgets.json at the repository root is a small file with a dual gate per operation: 

"window_reconciliation": {
  "baselineP95Milliseconds": 0.35,
  "absoluteBudgetMilliseconds": 2.0,
  "regressionPercent": 25
}

The gate is enforced by scripts/check-performance-regression.sh, and the condition is an AND, not an or check-performance-regression.sh:12: 

exit ! (current > absolute && current > baseline * (1 + percent / 100))

A measurement fails only when it breaches the absolute budget and sits more than regressionPercent above the recorded baseline. That combination is what makes the check usable in CI: a run that is 40 % above a 0.05 ms baseline is noise and stays silent because it is nowhere near the 1.0 ms cap, while a run that creeps toward the cap without moving off baseline is measurement drift rather than a regression. Only a genuine, large move trips both. Three operations are gated today — overlay_preparation (0.05 / 1.0 ms), window_reconciliation (0.35 / 2.0 ms) and state_persistence (0.10 / 2.0 ms) — all at 25 %. A benchmark that is missing from the current results is a failure in its own right :10, so deleting a measurement is not a way to pass.

The main-queue stall watchdog

MainQueueStallWatchdog Services/MainQueueStallWatchdog.swift:13 solves a problem that after-the-fact timing cannot:

A stall is only visible after the fact as a long duration, which does not say whether the main thread was busy or waiting. Sampling the process counters at the deadline answers that: CPU near zero with page-ins points at faulting or a lock, and CPU near a full core points at work. MainQueueStallWatchdog.swift:5-9

It is armed across an enqueue — before work is handed to main — and disarmed when that work completes. If the 250 ms deadline :37 fires first, it reports while the stall is still happening, with a resource delta measured across it. A generation counter makes a late deadline harmless, and the armed state is cleared in checkDeadline rather than in disarm so an already-fired deadline cannot resurrect.

Crucially: "Nothing is scheduled unless a presentation is in flight, so an idle Debut still runs no timers" :11-12. This is the same no-polling rule that governs the rest of the codebase.

Telemetry

Nothing leaves the machine in the stock build

setupTelemetry() AppDelegate.swift:925 resolves a TelemetryDeck namespace and app ID from the environment (DEBUT_TELEMETRYDECK_NAMESPACE, DEBUT_TELEMETRYDECK_APP_ID), falling back to Info.plist keys, falling back to the empty string. Both plist values ship empty Resources/Info.plist:5-8, so: 

let client: any TelemetryClient = namespace.isEmpty || appID.isEmpty
    ? UnavailableTelemetryClient()
    : TelemetryDeckClient(namespace: namespace, appID: appID)

A build made from this repository as-is has no network destination at all. The entire pipeline still runs, still enforces quotas, and still drops everything on the floor at the client boundary. That is a deliberate arrangement: the code path is exercised, the data is not sent.

The payload is an allowlist

TelemetryPayload Services/Telemetry.swift:113 has a hand-written CodingKeys enumerating every field that can be encoded: schemaVersion, event, appVersion, operatingSystemMajor, workload, temperature, operationCounts, latencyBuckets, anomalyCount, operation, latency. There is no field for a window title, bundle identifier, app name, file path, or user identifier — the shape of the type prevents them rather than a policy discouraging them. Even the client sends "clientUser": "" :197.

Continuous values are bucketed before they are ever assembled into a payload:

What counts as an anomaly

PerformanceAnomalyPolicy Telemetry.swift:17 is four lines and worth reading directly: 

public static let minimumDurationMilliseconds = 500.0

public static func shouldReport(_ observation: PerformanceObservation) -> Bool {
    observation.operation != .hiddenIdle
        && observation.durationMilliseconds >= minimumDurationMilliseconds
}

Half a second is the floor — nothing routine is ever a candidate. hiddenIdle is excluded because it measures how long the overlay stayed hidden, which is unbounded by design and would otherwise be reported constantly. shouldRetain applies the same exclusion at the queue, so a payload that predates the rule gets dropped rather than sent.

Quotas

TelemetryExporter Telemetry.swift:325 is an actor with two daily limits: dailyEventLimit = 20 and dailyPerOperationLimit = 2 :337-338. The per-operation limit is what stops one pathological operation from consuming the entire budget and hiding everything else.

There is also a reservation, which is easy to miss: 

let summaryReservation = dailyEventLimit > 1 && payload.event == .anomaly ? 1 : 0
guard quota.sent + payloads.count < dailyEventLimit - summaryReservation else { … }

Anomalies may fill at most 19 of the 20 slots, so the session summary always has room. Without it, a bad day produces 20 anomaly reports and no context to interpret them against. Dropped payloads are counted in the quota record rather than silently discarded.

The queue is behind a protocol with two implementations: InMemoryTelemetryQueue :253 for tests and DiskTelemetryQueue :264 writing telemetry-queue.json in Application Support. Quota decoding uses decodeIfPresent with defaults :243, so an older quota file does not throw. setEnabled(false) clears the queue immediately :348 — turning telemetry off discards what was pending, it does not merely stop adding to it.

TelemetryDeckClient.send :163 POSTs to https://nom.telemetrydeck.com/v2/namespace/<namespace>/ and treats anything outside 200..<300 as TelemetryError.rejected(statusCode:); a missing namespace or app ID is .invalidConfiguration. Latency buckets are flattened into dimension keys of the form Debut.operation.<op>.latencyBucket :193.

Privacy posture

Three artefacts describe what Debut can reach:

  • Resources/Debut.entitlements contains exactly one key: com.apple.security.app-sandbox = false. Nothing else is claimed. Debut cannot be sandboxed and do its job — the Accessibility API and ScreenCaptureKit both operate across process boundaries.
  • Runtime TCC prompts are the actual permission surface: Accessibility and Screen Recording, both requested at first use and both revocable in System Settings. Chapter 3 covers how the app behaves when they are denied.
  • Resources/PrivacyInfo.xcprivacy declares NSPrivacyTracking false with no tracking domains, and two collected data types — ProductInteraction and PerformanceData — both marked not-linked, not-for-tracking, and used for Analytics.

Reading the instrumentation in practice

  1. "What was the app doing?" — diagnostic.json, state block. It is current as of the last report from the main queue.
  2. "What led up to it?" — diagnostic.jsonl. Grep for the reason codes from chapter 7; check .jsonl.1 if the session was long.
  3. "Why was the overlay slow?" — the overlayPresentation traces in the snapshot. Find the phase pair with the large gap before assuming anything about the cause; the phase names are the hypothesis space.
  4. "Was it blocked or busy?" — the resourceDelta on the span, or a watchdog stall report. CPU near zero means waiting.
  5. "Is this only me?" — it is, as far as this build is concerned. Telemetry has no destination configured.

When instrumenting new code, the ordering rule from chapter 2 still applies: no workspace or cross-process Accessibility calls inside the event-tap callback, including from a reporter. Report the fact, let the main queue enrich it.
