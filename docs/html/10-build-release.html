Chapter 10

Build, install, release

There is no Xcode project. A shell script turns a SwiftPM executable into a signed .app, and the certificate it signs with is the reason Accessibility permission survives a rebuild.

The package

Package.swift declares swift-tools-version: 6.2 and platforms: [.macOS(.v26)], with no external dependencies at all — every line of third-party code in this project is zero lines. Five executables and one library:

ProductTargetPurpose
DebutDebutAppThe shipped app. A thin main over DebutCore.
—DebutCoreEverything. Depends on AXPrivate.
—AXPrivateC shim exposing _AXUIElementGetWindow; links ApplicationServices.
DebutE2EDebutE2EThe end-to-end harness (chapter 9).
DebutBenchmarksDebutBenchmarksEmits the benchmark JSON the budget gate consumes.
DebutPerformanceFixture—Drives repeatable input via DebutInputDriver.
DebutGlassLab—The Liquid Glass comparison lab (chapter 6).
—DebutInputDriverShared input sequences; used by the fixture and the test target.

The test target excludes Screenshots Package.swift:66 — those are PNG outputs sitting inside the sources directory, and SwiftPM would otherwise complain about unhandled resources.

This machine has a broken Swift Wasm toolchain earlier in PATH. A bare swift build or swift test will pick it up and fail in confusing ways. Always use: 

TOOLCHAINS=com.apple.dt.toolchain.XcodeDefault /usr/bin/swift

Every script in scripts/ already does this. The prefix is only needed when invoking Swift by hand.

Assembling the bundle

scripts/build-app.sh is short enough to read in full, and does five things in order:

  1. Build release. swift build -c release produces .build/release/Debut.
  2. Lay out the bundle. Create .build/Debut.app/Contents/{MacOS,Resources}, copy the binary, Info.plist, and PrivacyInfo.xcprivacy.
  3. Generate an icon. sips resizes the system GenericApplicationIcon.icns into an iconset at six sizes plus their @2x variants, and iconutil packs it. Every step is || true-guarded; a missing icon is not a build failure. There is no designed app icon yet.
  4. Sign. See below.
  5. Print the install command. The script never touches /Applications itself.

The minimum version is declared twice — once for the compiler in Package.swift, once for Launch Services in Info.plist — and they have to agree. They did not for a while: the package targeted .macOS(.v26) while the plist still said 14.0. Launch Services enforces the plist, so the looser number would have let a macOS 14 machine install and launch a binary compiled against the 26 SDK, and the failure would land on the user at whichever API turned out to be missing rather than on us at build time.

Tests/CI/PackagingTests.sh now derives the expected plist value from Package.swift and fails when the two drift, so bumping the platform cannot silently leave the plist behind.

Code signing

SIGN_IDENTITY=$(security find-identity -v -p codesigning | grep "Debut Dev" | head -1 | awk '{print $2}' || true)
if [ -n "$SIGN_IDENTITY" ]; then
    codesign --force --deep --sign "$SIGN_IDENTITY" --entitlements … "$APP_BUNDLE"
else
    codesign --force --deep --sign - --entitlements … "$APP_BUNDLE"
fi

Why a self-signed certificate rather than ad-hoc signing. TCC records an Accessibility grant against the app's designated requirement, derived from its signature. An ad-hoc signature (--sign -) is different on every build, so every rebuild looks like a new app and the permission resets — meaning you re-approve Debut in System Settings, and restart it, on every single iteration. A stable "Debut Dev" identity in the login keychain keeps the requirement constant, so the grant survives. The script says exactly this in its fallback message.

It is also what makes the E2E TCC pre-seeding in chapter 9 work at all: the csreq blob written into TCC.db has to keep matching the rebuilt binary.

If the certificate is missing, AGENTS.md carries the exact openssl / security import / add-trusted-cert recipe to recreate it. Note the entitlements file is passed in both branches — the sandbox must be explicitly disabled either way (chapter 8).

The install loop

TOOLCHAINS=com.apple.dt.toolchain.XcodeDefault /usr/bin/swift test
./scripts/build-app.sh
pkill -f "Debut.app" || true
rm -rf /Applications/Debut.app
cp -R .build/Debut.app /Applications/Debut.app
open /Applications/Debut.app

scripts/rebuild.sh is exactly the last five of those steps, with a one-second pause after pkill so the old process releases its event tap before the new one asks for one. It builds, installs, and launches — it never runs E2E.

Never leave code changes uninstalled. The installed app must always match the source. E2E runs against /Applications/Debut.app, and so does every manual observation; a stale bundle produces confident, wrong conclusions. This is a standing rule in AGENTS.md, not a suggestion.

rm -rf before cp -R matters: copying over an existing bundle can leave orphaned files from the previous version inside it, which invalidates the signature.

Performance runs

scripts/performance-test.sh is the gate described in chapter 8, wired end to end:

swift build -c release --product DebutBenchmarks | v .build/release/DebutBenchmarks > benchmarks-<UTC timestamp>.json | +--> jq -e . (fail fast if the JSON is malformed) +--> copy to benchmarks-latest.json | v check-performance-regression.sh PerformanceBudgets.json <artifact>

Artefacts land in .build/performance-results/ by default, overridable with DEBUT_PERFORMANCE_RESULTS. Timestamped names mean runs accumulate rather than overwrite, so a regression can be bisected against real historical measurements instead of remembered ones. There are Tart variants (tart-performance.sh, tart-performance-guest.sh) for running the same thing in the VM.

scripts/profile.sh wraps xcrun xctrace record against the installed app, defaulting to the Time Profiler template, with SwiftUI, Animation Hitches, Allocations, Leaks, System Trace, Swift Concurrency and App Launch also offered. Traces are timestamped into .build/profile-results/. It requires the app to be installed — another reason the install step is not optional.

Release checklist

docs/privacy-release-checklist.md is short and specific. Paraphrased:

  • Confirm PrivacyInfo.xcprivacy matches the actual binary and dependency inventory.
  • Snapshot the exact enabled payload and compare every key against TelemetryPayload — verify the allowlist empirically rather than trusting the type.
  • Verify disabled mode produces zero DNS, TCP and HTTP telemetry traffic. Not "no payloads sent" — no packets.
  • Verify opt-out deletes the on-disk queue without restarting.
  • Search the payload evidence for the documented denylist and for stable identifiers.
  • Confirm endpoint region, 90-day retention, dashboard access, and the daily cap.
  • Review dependency updates for automatically-added fields, capture, identity, replay, or endpoint changes.
  • Archive the payload snapshot, network trace, manifest, diagnostics, benchmark JSON and a selected Instruments trace with the release evidence.

The theme is that every privacy claim must be verified from outside the code. The type system prevents a window title from being encoded; the checklist requires you to prove it on the wire anyway.

What is not automated

Worth knowing before you look for it:

  • No notarisation, no distribution. The app is self-signed for local development. Shipping it to another machine would need a Developer ID and a notarisation step that does not exist here.
  • No version bumping. CFBundleShortVersionString is hand-edited.
  • No unit-test CI. The only workflow is e2e.yml. Unit and screenshot tests run locally, per the AGENTS.md workflow.
  • No designed icon. The build borrows a system icon.
  • No dependency management, because there are no dependencies.
