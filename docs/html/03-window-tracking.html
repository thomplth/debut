Chapter 03

Window discovery and tracking

Everything upstream of the space model. How Debut learns that a window exists, decides whether it is real, keeps a handle on it, and — the hard part — learns that it has gone away.

Two sources of truth, neither sufficient

macOS exposes windows through two unrelated APIs, and Debut needs both.

The Accessibility API
Gives structure: which application owns which windows, each window's role and subrole, whether it is modal, and — crucially — notifications when a window is destroyed, retitled, or focused. It does not give you a window ID.
CGWindowListCopyWindowInfo
Gives identity and geometry: a numeric CGWindowID, owner PID, bounds, title, on-screen flag. It has no notion of roles, cannot tell a real window from a shadow or a popup, and emits no events.

The bridge between them is a private but linkable symbol, _AXUIElementGetWindow, which maps an Accessibility element to a CGWindowID. The AXPrivate target exists only to declare it. Its .c file is empty apart from a comment:

Empty — _AXUIElementGetWindow is provided by ApplicationServices at link time. This module only declares the symbol so Swift can see it. Sources/AXPrivate/AXPrivate.c

The discovery pipeline

AccessibilityWindowService.listWindows() Services/AccessibilityWindowService.swift:55 is Accessibility-first and window-server-second:

1. NSWorkspace.runningApplications, filtered to .regular | v 2. For each app: AXUIElementCreateApplication(pid) -> kAXWindowsAttribute | v 3. For each AX window: read role and subrole | read fails -> skip entirely: NEITHER set (see below) v 4. _AXUIElementGetWindow(element) -> CGWindowID | bridge fails or ID is 0 -> skip: NEITHER set v 5. Read the modal flag, then classify: | +--> isTrackableAXWindow(role:subrole:isModal:) ? yes -> trackable set no -> untrackable set | v 6. CGWindowListCopyWindowInfo([.optionAll, .excludeDesktopElements]) | v 7. Keep only IDs in the trackable set; join with PID -> bundle ID / app name | v 8. [WindowInfo] (windowID, ownerPID, bundleID, name, title, bounds, isOnScreen)

The classification predicate

isTrackableAXWindow(role:subrole:isModal:) AccessibilityWindowService.swift:127 is a static pure function, which is why it can be unit-tested exhaustively without a running window server. A window is trackable when its role is kAXWindowRole, its subrole is either kAXStandardWindowSubrole or kAXDialogSubrole, and it is not modal.

Three outcomes, not two

A window whose role/subrole read fails, or whose window-ID bridge fails, lands in neither the trackable nor the untrackable set. That omission is what makes a partial snapshot non-destructive: an unreadable window is simply not mentioned, rather than being asserted to be junk. The distinction matters because an application still warming up will happily report a standard window as a dialog for a few hundred milliseconds.

The consequence for the space model is a rule stated in AGENTS.md and enforced here: an untrackable classification makes an assignment dormant, never deleted. Deleting turns a momentary misreport into permanent layout loss — it once stranded a browser's four windows, which then reappeared as brand-new windows and collapsed into the active space.

The snapshot that can say "I don't know"

listAllWindowIDs() AccessibilityWindowService.swift:119 runs the same window-server query with no Accessibility filter and returns an optional set. nil means the snapshot failed. This is not defensive nicety: the reconciler uses the presence of a window ID in this set as evidence that an ID may have been recycled, and a failed snapshot must never be read as "every window is gone".

Preview capture

Capture is the only asynchronous part of the window service. captureWindowImages(windowIDs:onEnumerated:onCapture:) AccessibilityWindowService.swift:185 uses ScreenCaptureKit exclusively:

  1. Await a shared SCShareableContent snapshot from ShareableContent.shared.
  2. Intersect its window list with the requested IDs and fire onEnumerated immediately, so callers can separate "waiting for ScreenCaptureKit to enumerate" from "waiting for pixels". Those two costs are wildly different and conflating them hides regressions.
  3. Issue one SCScreenshotManager.captureImage per window inside a withTaskGroup, each with an SCContentFilter(desktopIndependentWindow:).
  4. Report each success individually through onCapture :249. A failure does not abort the batch and does not call back at all — it is recorded as a diagnostic, so a missing preview is silent to the caller and visible in the log.

Images are downsampled to at most 640 pixels on the long edge. The reason is memory, not speed, and the code says so: a full-resolution capture of a Retina display is roughly 50 MB, and the cache holds one per window. Capture time is per-window and essentially independent of the requested size, so asking for a smaller image buys nothing but bytes.

The shareable-content cache

ShareableContent Services/ShareableContent.swift wraps the enumeration in a RecentValueCache actor that caches for 500 ms and coalesces concurrent loads through a single in-flight Task. A failed load is deliberately not cached. The type is also where a counter-intuitive API detail is pinned down:

Flag polarity

SCShareableContent.excludingDesktopWindows(true, …) describes the returned list, not your intent. Passing true keeps desktop windows out of the list, which is what you want before handing the list to SCContentFilter(display:excludingWindows:) to capture the wallpaper. Passing false puts the wallpaper in the list, and then excluding it leaves the filter with nothing to composite — which fails at capture time with error -3811, not at filter construction.

Observers: knowing when things change

Discovery is a snapshot. Everything after the first snapshot is event-driven — there is not a single timer in this layer. Two families of Accessibility observer do the work, and they are structured differently on purpose.

The focus observer — one at a time, follows the frontmost app

installFocusObserver(for:) Services/WindowDiscoveryService.swift:448 creates a single AXObserver on the frontmost application's element and registers kAXFocusedWindowChangedNotification. Its run-loop source is attached to the main run loop in default mode. It early-returns if the observer already belongs to that PID and tears down the previous one otherwise. Filtering out Debut itself and excluded bundles happens in the callers :249, :546, not in the installer.

It moves whenever NSWorkspace.didActivateApplicationNotification fires. One observer, always on the app you are using. This is what makes MRU ordering and "new window joins the active space" work without polling.

The lifecycle observers — one per PID, registered per window

getOrCreateObserver(for:) WindowDiscoveryService.swift:370 memoises one observer per process. armWindow(windowID:pid:element:) WindowDiscoveryService.swift:317 then registers, on the individual window element:

  • kAXUIElementDestroyedNotification — the only proof that a window closed. Registration failure here is a real failure.
  • kAXTitleChangedNotification — the result is deliberately discarded, with the comment "A stale title is cosmetic, so it never gates tracking."

A retry after a partial failure reports the destroy notification as already registered; that error is treated as success.

Arming, and the failure that used to be permanent

"Arming" is the term for successfully registering that destroy notification. The state machine around it is small but carries a scar: 

enum WindowArmingOutcome {
    case armed
    case observerUnavailable
    case elementUnavailable
    case notificationRejected(Int32)
}

WindowDiscoveryService.swift:8

On failure, the window ID is inserted into unarmedWindowIDs and removed from knownWindowIDs. The comment explains why that removal is the point:

Leaving the window out of armedWindowIDs is what allows the next activation to retry. Recording it as tracked regardless is what previously made a transient AX failure permanent. WindowDiscoveryService.swift:303

Each outcome maps to a distinct tracking_failed diagnostic step, so a failure is attributable after the fact rather than inferred. The unarmed set is also propagated into the reconciler's snapshot, described there as "windows currently assigned without an armed destroy notification, so nothing can ever prove they closed" — the reconciler needs to know which assignments are structurally unfalsifiable.

Pruning

pruneTracking(runningPIDs:) WindowDiscoveryService.swift:398 drops observers for processes that are not in the set it is handed. The essential hack lives in the caller: handleAppActivation :576 force-inserts the activating PID before calling it, because Launch Services has not necessarily published a freshly activated process into runningApplications yet. Without that insertion, the app you just switched to can have its observers pruned microseconds after they were installed.

removeAppObserver(for:) clears the per-window arming records before looking up the observer, because "arming records are keyed by window, not by observer, so they must be cleared even when no observer was ever created for this app."

Process exit monitoring

An Accessibility observer cannot tell you that a process died — the observer dies with it. So Debut watches processes directly. ProcessExitMonitor Services/ProcessExitMonitor.swift:10 is 40 lines around one kernel primitive: 

DispatchSource.makeProcessSource(
    identifier: pid,
    eventMask: .exit,
    queue: .main
)

One source per PID, stored in a dictionary, resumed after the handler is set, cancelled on stop and in deinit. Because delivery targets the main queue, the handler needs no thread hop.

NSWorkspace.didTerminateApplicationNotification is kept as a backup signal, so both paths funnel into one idempotent method, handleProcessExit(pid:) WindowDiscoveryService.swift:616, gated on inserting into a handledExitedProcessIDs set. It stops monitoring, drops the focus observer if it belonged to that process, removes the app observer, and notifies the policy layer — which converts the window assignments to dormant rather than deleting them.

Ordering that matters

PID monitoring is registered before Accessibility arming is attempted. Monitoring must not depend on per-window Accessibility success, or an app whose windows failed to arm would also lose its exit detection — the two failure modes would compound. Two separate tests pin this: that monitoring is registered when arming fails, and that pruning observers does not discard monitoring.

Discovery paths and the ghost-window rule

There are exactly three ways a window enters the model, and all three must register tracking. Missing any one produces a "ghost": a window on a stage that Debut can never learn has closed.

PathTriggerNotes
Startup reconciliation reconcileWindows during setupController Matches persisted assignments against the live list. See chapter 7.
App launch NSWorkspace.didLaunchApplicationNotification Deferred by launchDiscoveryDelay (0.5 s in production, 0 in tests) because a just-launched app has no windows yet.
Focus change kAXFocusedWindowChangedNotification The Cmd+N path. A window created outside Debut's awareness gains tracking at the moment it takes focus.

The empty-snapshot bailout

reconcileWindows WindowDiscoveryService.swift:180 returns early with a windows_reconcile_skipped diagnostic when the live window list comes back empty while persisted windows and running applications both exist. As the comment puts it, treating that snapshot as authoritative would erase every saved space assignment. This is the same principle as the tri-state classification: an absence of evidence is not evidence.

Sampling order on activation

handleAppActivation WindowDiscoveryService.swift:555 samples the focused window before enumerating windows, so that "transient activation windows are not introduced by reconciliation latency". The callback order is asserted by test as ["app:<bundleID>", "snapshot", "focus"] WindowDiscoveryServiceTests.swift:77: reconciliation must be published before focus, which is precisely what lets the reconciler see a replacement window as still unassigned and match it to the right space.

The runtime tables

WindowDiscoveryService keeps several plain dictionaries and sets, all runtime-only. The armed and unarmed sets carry the explanation WindowDiscoveryService.swift:36 — "every window re-arms from scratch on launch, so this never reaches state.json" — and the same reasoning applies to the rest:

TableHolds
knownWindowIDsWindows discovery believes it has seen and tracked.
armedWindowIDsWindows with a live destroy notification.
unarmedWindowIDsWindows whose arming failed; retried on next activation.
trackedWindowElementswindowID → AXUIElement. Doubles as the fast path for raising a window without rescanning.
perAppObserversPID → AXObserver.
monitoredProcessIDs / handledExitedProcessIDsExit-monitor bookkeeping and its idempotence guard.

Reverse lookup from an AXUIElement back to a window ID (needed in the destroy callback, which receives only the element) is a linear scan comparing with CFEqual. It runs once per window close, so the cost never mattered enough to index.

The known, armed, unarmed and monitored-PID sets are exported through diagnosticTrackingSnapshot WindowDiscoveryService.swift:43, which is how the E2E suite and a bug report can both tell "Debut thinks it is tracking this window" apart from "Debut is actually armed on it". The observer and element dictionaries are not exported — they hold live AXUIElement references with nothing serialisable to say.

Equality is identity, not content

== on SpaceWindow compares only windowID. A title change does not make two values unequal, and two different windows with the same ID are the same value. Code that needs to distinguish entries — the reconciler in particular — keys its sets by window.id, not by the value. The same shortcut applies to Space, whose == compares only its id.

DormantWindowAssignment is a SpaceWindow plus the spaceID and the windowIndex it should return to. It forwards its id to the wrapped window's. Chapter 7 covers how it is decoded, pruned, and restored.
