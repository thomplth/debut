Chapter 06

The overlay

The only part of Debut a user actually looks at. An AppKit window hosting a SwiftUI tree, laid out by hand-written geometry, animated as a pure render transform, and rebuilt by assignment rather than observation.

The window

OverlayWindow Views/OverlayWindow.swift:4 is borderless, at .statusBar level, non-opaque with a clear background and no shadow, and its collection behaviour is [.canJoinAllSpaces, .fullScreenAuxiliary].

Opposite of the desktop surface

Note the contrast with chapter 4: the desktop surface must not join all Spaces, because following you into a full-screen Space would cover the app. The overlay must, because it should be reachable wherever you are.

It never becomes key, and the comment explains why that is a decision rather than an oversight:

A borderless window cannot become key, and Debut is an accessory app that is inactive when the overlay opens. Asking for key status buys nothing and makes the ordering conditional on app activation. OverlayWindow.swift:63

So it uses orderFrontRegardless() plus a 0.15 s ease-out alpha ramp to reveal, and a 0.1 s ease-in ramp to hide. Keyboard input never goes through the window at all — it arrives via the event tap.

Attaching and detaching the hosting view

Hiding the overlay does not just order the window out; it removes the NSHostingView entirely and nils it.

The 50% CPU bug

SwiftUI keeps running layout passes on a hosting view attached to an ordered-out window. Leaving it attached measured as more than half a core consumed while the overlay was invisible. Removing the hosting view on hide and recreating it on show is not an optimisation — it is the fix.

update(viewModel:) returns a Bool meaning "I had to create the hosting view", which the caller feeds into presentation telemetry as created versus reused. That single bit is one of the strongest predictors of cold-versus-warm overlay latency, which is why it is recorded rather than inferred. Every update also re-synchronises the window frame to the main screen first.

No observation anywhere

OverlayViewModel Views/OverlayViewModel.swift:20 is a plain Sendable struct — not @Observable, not ObservableObject. Its stages property is computed on every access by mapping the space model into StageData and StageWindowData. Refresh means: build a whole new value, assign it as rootView. The only @Observable type in the UI is the onboarding view model, where the reactive ergonomics are worth it and the performance is irrelevant.

Layout mathematics

Static geometry lives in StageConstants Views/StageView.swift:615; the values governing the stack's depth falloff live in StageMotion :57. The important ones:

ConstantValueRole
thumbnail160 × 100Maximum preview size; aspect ratio 1.6 is fixed
windowSpacing12Between previews inside a stage
padding24Stage inset; top and bottom padding are equal by design
minStageWidth300Floor for a nearly empty space
badgeSize40App icon badge on each preview
stageSpacing34 / 14Vertical gap — the larger value only when the active stage shows footer hints
StageMotion.minimumStageScale0.08Floor so distant stages never collapse to nothing

Horizontal: fitting the widest stage

thumbnailSize(forWindowCount:screenWidth:) divides the available width by the window count, subtracts per-card padding and title allowance, and clamps the result to 80…160, deriving the height from the fixed aspect ratio. A stage's width then exactly fits its own cards; each stage is a different width, and that is intentional — stage width communicates how many windows a space holds.

Vertical: the stack

StageMotion.stackLayout(spaceCount:focusIndex:stageHeight:spacing:inactiveScale:) StageView.swift:139 is a pure function — which is why there are 44 unit tests for the motion maths and no need to render anything to check them. 

scale(i)   = max(pow(inactiveScale, |i - focusIndex|), 0.08)
height(i)  = stageHeight * scale(i)
centers    accumulate top-down with `spacing` between them
opacity(i) = 1, until scale drops below 0.2, then fades quadratically to 0.12

Scale compounds with distance rather than being a two-state active/inactive value, which is what gives the stack its depth.

Anchoring: why hovering does not shove the stack

The body computes the layout twice: a baseline layout focused on the active space, and a visual layout focused on the currently focused index (which may be a hovered or drag-targeted stage). It then finds where the focused stage sits in the baseline and offsets the visual layout so it lands exactly on that anchor.

The effect: hovering an inactive stage expands it in place instead of displacing everything else. The focus index itself is a small precedence chain — drag target, then retained drag target, then hover, then active.

Animation, and the render-transform rewrite

Space focus changes animate as .spring(duration: 0.26, bounce: 0.08); window reordering uses a slightly longer, flatter spring. Under Reduce Motion both become short fades, and the transition strategy changes wholesale — the subtree gets an identity keyed on the active space index with an opacity transition rather than spatial motion.

A window card arriving at or leaving a stage scales and fades over .spring(duration: 0.28, bounce: 0) — no bounce, because overshoot on a departing card reads as the window trying to come back StageView.swift:94. That animation is keyed on the stage's window count, deliberately not on its window IDs: a drag reorder permutes the IDs while holding the count, so keying on IDs would hijack the reorder's own motion.

Getting the card to leave at all needs a push from outside SwiftUI. Neither the window-destroyed nor the process-exit path used to refresh a visible overlay, so a quit app's card sat there until some unrelated redraw. Both now call SpaceController.handleLiveWindowsRemoved, which clamps selectedWindowIndex back into range — it is an index into a list that just got shorter — and redraws. Both paths matter: quitting an app usually delivers the Accessibility destroyed notification before the process actually exits, so whichever lands first has to do the work.

Scaling used to be a layout change

Originally each stage's .frame was set to stageHeight × scale, and the glass surface size and corner radius were pre-multiplied by scale too. Every interpolated frame of the spring therefore changed layout inputs, forcing SwiftUI to re-solve the tree on every tick of the animation.

Now every stage lays out in an identical unscaled slot inside a top-aligned ZStack, and an offset shifts that slot so the scaled stage lands on its stack centre. Scale is applied as .scaleEffect — a render transform the compositor handles, with no layout involvement. Measured result: 1.88 ms → 1.49 ms per layout pass, and 1405 versus 1124 frames delivered in the same wall time, with byte-identical rendered output.

The modifier order matters and is easy to break: 

.background(StageSurfaceView(unscaled size, unscaled radius))
.background(GeometryReader -> StageFramePreferenceKey)
.scaleEffect(scale)
.shadow(...)
.opacity(...)
.offset(y: stageSlotOffset)

The geometry reader sits beneath scaleEffect, so the frames it publishes are still the on-screen scaled rectangles. That is what keeps hit testing correct for the pointer and the drag targets after the rewrite.

Window previews

Capture itself is chapter 3. What lives here is the caching policy, in windowIDsNeedingCapture() Services/SpaceController.swift:762:

The whole policy is gated on previewRefreshPolicy == .lastActiveOnly :764. Under any other policy every assigned window is re-captured, and the rules below do not apply. When the policy is active:

  • Always re-capture the active space's front window — the one that was just being used, and therefore the one most likely to look stale.
  • Re-capture when the window's title has changed since the cached image.
  • Re-capture past the cache TTL (default 60 s, configurable 5–600).
Dirty tracking alone goes stale for windows that change without ever being activated — video, chat, dashboards. SpaceController.swift:770

Windows with no preview render a rounded rectangle with a 32 pt application icon. AppIconImage is an NSViewRepresentable around NSImageView that resolves the icon from the bundle identifier and falls back to drawing a two-letter monogram. Note that each card can render two of these — the badge and the placeholder — and that these representables are currently the dominant cost when cycling stages.

Pointer interaction

Selecting

A press below 6 pt of movement is treated as a click and selects the window; beyond that it becomes a drag. Both come from one DragGesture(minimumDistance: 0) in a named coordinate space, attached as a high-priority gesture.

The stationary pointer problem

The overlay appears under wherever the cursor happens to be resting. Without care, that immediately hijacks the keyboard selection. PointerMovementGate StageView.swift:591 seeds itself with the mouse location at view construction and swallows hover events until the physical mouse actually moves. There is both a unit test and an E2E scenario for it.

Hover also has hysteresis: focus is retained while the pointer is in the vertical gap between two stages and inside a horizontal corridor interpolated between their widths, so moving diagonally between stages does not flicker.

Dragging a window between spaces

The drop target is the first stage whose frame contains the point; the insertion index comes from comparing the pointer's x against each remaining card's midpoint. Live feedback is offset-only — gaps open and close, the shrinking source stage re-centres, and stage widths pre-adjust to their post-drop window counts — so nothing in the model changes until release.

Release is a three-phase handoff, and the phases exist because the model update is asynchronous:

1. animate the dragged preview to its destination position 2. on completion: store a "settling" state, then call onWindowMoved -> the delegate mutates the model and rebuilds the view model 3. clear the drag state only once the layout preference key proves the move actually applied, inside a transaction with animations disabled -> without this the card animates twice, once per representation

The target stage stays magnified across that gap via a retained focus index. On the delegate side, the overlay rebuild is deliberately deferred by one run-loop hop: "let SwiftUI finish the drag transaction before replacing its root view."

Why spaces cannot be reordered

The overlay once let a stage be dragged by a handle to reorder the stack. A space is now the desktop at its index, so reordering spaces means reordering desktops — and while SLSMoveManagedSpaceToDisplayIndex does reorder a desktop instantly and with no visible transition, the Dock keeps navigating by its own stale copy of the order, which misdirects the forged swipe that switches a space. The new order also does not survive a reboot: three VM trials reverted it, with com.apple.spaces never taking it in four minutes of polling and killall Dock making no difference. A reorder that is neither transparent nor durable is worse than none, so the handle, its reveal zone and its slot-based drag were removed rather than rebuilt on a stored permutation.

The window drag remains, and emits window_move_previewed_by_drag — which is how the E2E harness verifies it without reading pixels.

Liquid Glass

Production glass is one modifier: .glassEffect(.clear or .regular, in: .rect(cornerRadius:)) on macOS 26, falling back to a semi-transparent ultra-thin material. Which of the two styles is used is a user setting.

Settings and onboarding

The Settings window is a 700×500 panel with a full-size content view, hidden title, and transparent titlebar. The sidebar is a NavigationSplitView whose selection drives a ScrollViewReader — every section carries an id and selecting one scrolls to it. It is one continuous scrolling document, not a set of panes, so the sidebar highlight follows the scroll position as much as it drives it.

Live apply is a single onChange on the whole settings value at the root: any mutation persists and fans out to discovery exclusions, key bindings, presentation delay, preview policy and TTL, quick-switch modifiers, and telemetry. Nothing requires a restart.

Onboarding uses an injected permission client protocol so the flow is testable without touching TCC, and re-polls permissions on didBecomeActiveNotification — that is how returning from System Settings updates the cards. Starting the tutorial requires both Accessibility and Screen Recording; Screen Recording is marked required because it feeds the wallpaper capture as well as previews. A launch policy migrates the legacy "has launched before" flag so existing users never see a first-run screen.

Things that will surprise you

Selection style is configurable

The default filled selector uses RGB 103 in dark appearance and RGB 167 in light appearance at full opacity. It sits behind the preview and app icon, occupies the preview's reserved outset, never covers the title, and is suppressed on drag previews. Magnify retains the original 1.06× scale and adaptive dark/light shadow as defaults. Selector settings expose fill outset and radius or magnify scale and shadow strength, depending on the chosen style. Settings files written before these controls decode to the filled defaults. The short-lived Outline value also migrates to Filled.

  • Magnify shadows are not just inverted in dark mode. Dark uses 0.5 opacity / 14 radius / 6 offset against light's 0.24 / 8 / 4, with the comment that "a black shadow over the dark stage behind it needs more density and spread to read as depth than it does in light mode."
  • Space spacing depends on hint visibility. Turning command hints off changes the vertical geometry of the whole stack, from 34 pt to 14 pt.
  • StageConstants.stageCenterY is a second implementation of the stacking maths, deliberately independent of the layout path and kept for tests and the E2E harness to verify against. If you change the layout algorithm, change both — that redundancy is the check.
