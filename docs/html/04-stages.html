Chapter 04

Stages and switching

The model that holds the stages, the controller that acts on the system, the exact sequence that makes a stage switch look instantaneous, and the full-screen window that makes the whole approach possible.

A pure model and an impure controller

The split here is the cleanest boundary in the codebase and worth internalising before reading either file.

StageManagerStageController
Kind struct … Codable, Sendable Models/StageManager.swift:14 final class … @unchecked Sendable Services/StageController.swift:151
Imports Foundation, CoreGraphics. Nothing else. AppKit, Accessibility, the window and keyboard services.
Holds stages, activeStageID, dormantWindowAssignments The StageManager value, services, preview cache, overlay state, and the selection

The distinction that trips people up: the model tracks the committed active stage; the controller tracks the tentative overlay selection, in selectedStageIndex and selectedWindowIndex. While the overlay is open those two disagree, and that is the point — moving the selection must not switch stages. They reconcile in commitSelection() when the modifier is released.

Because the model is a struct stored on a class, external code mutates it through an inout reference to a property. That creates one real hazard, which the code names:

Rebuild into a local copy so discovery diagnostics can read controller state without an overlapping exclusive access. paraphrasing StageController.swift:306

There is a regression test called windowCacheResetAvoidsExclusiveAccessCrash guarding exactly that.

The activation sequence

switchToStage(id:raiseWindowID:) StageController.swift:245 is the single entry point for becoming a different stage, and its ordering is the core trick of the product.

1. Clear any in-flight same-app cycle state. -- everything below only if the target differs from the current stage -- 2. Record previousStageID; stageManager.activateStage(id:) the model flips first, so anything reading state sees the new truth 3. desktopSurfaces.orderToFront() the full-screen surface jumps above EVERY window: total occlusion 4. For each window in the target stage: windowService.raiseWindow(windowID:) AX-raises them back above the surface, in MRU order 5. Emit the stage_switched diagnostic -- always, even for a same-stage commit -- 6. Focus one window: raise it, bringWindowToFront in the model, then exactly ONE NSRunningApplication.activate(bundleID:)

Three details make it work:

  • Surface first, then raise. Occlusion is achieved purely by z-order. No window is moved, resized, minimised, or hidden, so there is no animation to wait for and no layout to restore. This is the whole reason the desktop surface exists.
  • One activation, at the end. An Accessibility raise only reorders a window within its own application's stack — it does not bring the application forward. The trailing activateApp does that. Doing it per window would produce a visible flash of each app in turn; the code comment is simply "single activation, no flash".
  • Steps 2–5 are skipped for a same-stage commit. The whole block, from recording previousStageID through raising the stage's windows, sits behind a previousID != targetID guard StageController.swift:263. Choosing a different window inside the current stage must not reshuffle z-order for everything else.

MRU is the array

There is no separate recency list. Stage.windows is the MRU order, most recent first, and the only mutator is Stage.bringWindowToFront(windowID:) Models/Stage.swift:54, which removes and reinserts at index 0.

Four events promote a window:

  • recordWindowActivation when the window is already in the active stage
  • a tap of the activation shortcut
  • committing a same-app cycle (the cycle raises windows live but only commits MRU on release)
  • the focus step of switchToStage

Selection defaults read straight off that ordering. openOverlay(selectNextWindow:) StageController.swift:577 sets the selected index to 1 — the second most recent window — unless the stage has fewer than two windows, or the frontmost application is excluded from Debut. In the excluded case there is nothing to skip past, so index 0 is correct. The exclusion flag is pushed in from the delegate, never queried.

Assignment: the three-branch core

recordWindowActivation(windowID:) StageController.swift:323 is where the assignment rules from chapter 1 actually live: 

owner stage == active stage   ->  promote in MRU, nothing else
owner stage != active stage   ->  switchToStage(id: ownerStageID, raiseWindowID: windowID)
no owner at all               ->  look the window up in the window service,
                                  build a StageWindow, add it to the ACTIVE stage

The third branch is annotated with its motivating case: code . creating a new editor window while other windows of that editor live in a different stage. The new window belongs where you are, not where its siblings are.

There is one short-circuit at the top: while a same-app cycle is in flight, activations of windows inside that cycle are ignored, so the Accessibility focus callbacks the cycle itself generates cannot scramble the MRU order mid-cycle.

Stage mutations

Create StageManager.swift:66
Inserts at the active index (above) or after it (below) and immediately activates the new stage. The controller first activates the selected stage, because insertion is relative to activeStageID and the overlay selection may have moved.
Delete StageManager.swift:81
Deleting the only stage wipes and recreates a fresh default rather than leaving zero stages. Otherwise the overflow target is index 1 when deleting index 0, and index - 1 in every other case; the windows are appended to that stage before the removal, and the active stage follows them.
Move a window StageManager.swift:276
moveWindow(windowID:fromStageID:toStageID:at:) appends when at is nil and inserts at an index otherwise — which is how a drag preserves the position you dropped at. Its guard permits a same-stage move precisely when an index is supplied, which is what makes in-stage reordering by drag possible.
Swap and reorder StageManager.swift:109
Neither touches activeStageID. Because labels are positional, reordering needs no further bookkeeping — but the controller must fix up its own selectedStageIndex, and the drag path re-finds the index by stage ID afterwards.
Prune StageManager.swift:138
removeEmptyStages() keeps any stage holding dormant assignments, and keeps everything if all stages are empty. There is always at least one stage.
Known rough edge

In deleteStage StageManager.swift:94, the new active index is computed as min(overflowIndex, stages.count - 1) against post-removal indices, while overflowIndex was computed pre-removal.

Deleting the stage at index 0 when three or more stages exist sets overflowIndex = 1, moves the windows into that stage, then removes index 0 — which shifts the overflow destination down to index 0. min(1, count-1) then activates the stage after the one that received the windows. Deleting any non-zero index is correct, because index - 1 is unaffected by the removal, and deleting index 0 of exactly two stages is correct by coincidence of the min.

StageManagerTests.swift has three deleteStage tests (:55, :360) and none of them asserts activeStageID for this case. spec/stage-manager.md:105 says the active stage should follow the overflow, so the code looks wrong — but verify against the spec before you "fix" it.

The desktop surface

DesktopSurfaceWindow Views/DesktopSurfaceWindow.swift:276 is an NSWindow subclass, one per display, coordinated by a DesktopSurfaceCoordinator. The add/remove/reframe decision when displays change is a pure function, DesktopSurfacePlan.plan(existing:screens:), so multi-monitor behaviour is unit-testable without monitors.

Yielding to a file drag

The surface covers the real desktop, which means it also covers Finder's drop target. Dragging a file "to the desktop" would otherwise silently do nothing.

The content view registers for .fileURL drags only. On draggingEntered with a file URL it fires a callback exactly once (latched, so a drag moving in and out does not retrigger) and reports .copy. performDragOperation then deliberately returns false: "the surface yields during draggingEntered so Finder handles the actual drop." The yield itself is ordering the surfaces out and hiding other applications, so the real desktop is exposed while the drag is still in flight. The latch is reset the next time the surface is ordered to front.

Wallpaper

The surface has to draw the wallpaper itself, and the wallpaper cannot be read from configuration — modern providers generate images and expose no file, so both the wallpaper store and desktopImageURL are dead ends. Debut captures the pixels macOS already rendered, via a ScreenCaptureKit filter that excludes all UI windows.

Two hard-won behaviours around it:

  • A failed capture keeps the last good image. "Clearing here would flash the surface black on a transient failure, which is the very symptom this window exists to avoid."
  • Change detection is a filesystem watch, not a notification. The old com.apple.desktop notification is dead. The wallpaper store's plist is replaced rather than modified, so the watch descriptor must be on the containing directory, and a two-second settle window collapses the three writes macOS emits per change into one refresh.

Talking to the rest of the app

Downward, the controller uses a weak StageControllerDelegate with six methods. Two of them have overloads carrying an OverlayPresentationContext? so a UI update can be correlated with the trace that caused it; protocol-extension defaults forward the context-free versions, so a conforming type only implements what it needs. Two further hooks — "a command was used" and "reveal the desktop" — are plain closures, because they did not justify protocol methods.

Upward, the controller is the keyboard delegate. handleKeyEvent(_:overlayPresentation:) StageController.swift:399 is one switch over the DebutKeyEvent enum, and it is where every interaction in chapter 5 lands.

Overlay visibility is mirrored back into the tap by direct property assignment at five call sites — setup, commit, discard, desktop reveal, and quick switch. That mirror is what lets the tap decide whether to consume a key without asking the main thread anything.

Performance-shaped decisions

Three pieces of this file exist in their current form because of measurements, not taste. They are documented in the source and repeated here because they are easy to "simplify" back into a regression.

Capture strictly after the first frame

Preview capture is kicked off after the delegate has been told to open the overlay. Capturing earlier puts ScreenCaptureKit enumeration, capture completions, and the resulting view rebuilds on the main queue ahead of the overlay's first frame — measured at roughly 37 ms of added render-submission delay for a two-line change.

Preview results are coalesced

Completions are batched into one rebuild per ~16 ms frame. Without it, a 15-window refresh becomes 15 full SwiftUI diffs.

The focus probe has a per-element timeout

Before showing the overlay, the controller asks the frontmost app where its focused window is and whether that window owns a full-screen Space — one round-trip, because this is the hot path. An unresponsive app would hang that question, so the Accessibility messaging timeout is bounded at 50 ms — and it must be set on both the application element and the focused-window element, because "it is scoped to the element ref it is set on, not to the app's connection."

Finally, preview pruning follows the same rule as assignments: only previews whose window has no assignment at all are dropped, because a missing capture can mean the window is merely hidden.
