Chapter 02

Architecture

How the program is put together: the package targets, the composition root, who depends on whom, how the layers talk, and which thread everything runs on.

Package layout

Everything is SwiftPM. There is no Xcode project, no storyboard, and no @main attribute. Package.swift declares two plain library targets, a C shim, and five executables:

TargetKindPurpose
DebutCorelibraryEverything: models, services, views. All logic lives here so it can be unit-tested without launching an app.
AXPrivateC targetA one-line shim declaring _AXUIElementGetWindow so Swift can see a symbol ApplicationServices already exports.
DebutAppexecutableThe shipped app. Seven lines of main.swift.
DebutE2EexecutableThe end-to-end harness. Drives the installed app with synthesized input.
DebutBenchmarksexecutableIn-process CPU benchmarks gated against budgets.
DebutPerformanceFixtureexecutableSpawns synthetic windows and drives input, for profiling under controlled load.
DebutDemoexecutableDrives the repeatable screenshots and clips used in the README.
DebutInputDriverlibraryThe synthesized-input sequence shared by the fixture and its tests.

Inside DebutCore the folders are the layers: Models/ holds value types with no side effects, Services/ holds everything that talks to the system, and Views/ holds AppKit windows and SwiftUI views.

Mocks ship in the library

MockWindowService and MockKeyboardService live in Sources/DebutCore/Services/ as public production files, not in the test target. That is deliberate: the protocol seams and their doubles are part of the library's contract, and the executables can use them too.

The composition root

Sources/DebutApp/main.swift creates NSApplication.shared, assigns an AppDelegate, and calls run(). Everything else is assembled by AppDelegate Sources/DebutCore/AppDelegate.swift:7, which is @MainActor and holds every long-lived object as an optional property. It is the only place in the codebase where concrete types are chosen.

Phase 1 — applicationDidFinishLaunching

AppDelegate.swift:44

  1. NSApp.setActivationPolicy(.accessory). Combined with LSUIElement in the Info.plist, this is what makes Debut an agent with no Dock icon and no menu bar of its own.
  2. Report app_launched to diagnostics.
  3. Build the StateStore, wrap it in a DebouncedSaver, and load both files. Both loads fall back to defaults on failure, so a corrupt file degrades to a fresh start rather than a crash.
  4. Configure telemetry.
  5. Construct AccessibilityWindowService, EventTapKeyboardService, OverlayWindow, and the menu bar item.
  6. The permission gate. If AXIsProcessTrusted() is already true, continue to phase 2 immediately. Otherwise register for activation notifications and wait — either for onboarding to finish or for the user to grant Accessibility in System Settings. Everything in phase 2 is useless without that permission.
  7. Report app_ready and open the hiddenIdle performance span, which stays open until the first overlay appears.

Phase 2 — setupController()

AppDelegate.swift:89

This is the interesting half, and its order encodes several constraints:

  1. Create WindowDiscoveryService over the window service.
  2. Wire windowService.windowElementResolver back into discovery. This is a deliberate cycle, broken with a weak reference: it lets raiseWindow reuse the Accessibility element discovery already cached instead of rescanning every application on every raise.
  3. Apply the exclusion list before anything is discovered.
  4. Reconcile the persisted space manager against live windows, inside a windowReconciliation performance span.
  5. Remove excluded bundles, prune empty spaces, and populate a default space only if everything is empty and there are no dormant assignments. A user who has quit every tracked app still has a layout worth keeping.
  6. Determine the starting space from the currently focused window rather than defaulting to space 1.
  7. Create the DesktopSurfaceCoordinator and order it to front before the controller exists, so the controller's first space switch can raise windows above a surface that is already in place.
  8. Construct SpaceController. Its initialiser starts the event tap and installs the diagnostic state provider.
  9. Attach the discovery callbacks and call startObserving().

The dependency graph

AppDelegate @MainActor (composition root, SpaceControllerDelegate) | owns ----------------+----------------------------- owns | | | | | v v v v v StateStore WindowDis- Overlay DesktopSurface SpaceController + Debounced covery Window Coordinator | Saver Service | owns | v | closures SpaceManager | (onAppLaunched, onWindowClosed, (pure value type) | onFrontmostAppChanged, ...) | v | uses AccessibilityWindowService <---------------- WindowService + ProcessExitMonitor KeyboardService (protocol seams) | weak delegate | AppDelegate <--------------------+

Two things to notice. WindowDiscoveryService never talks to SpaceController directly — it exposes closures that AppDelegate attaches, so policy decisions about what a discovery event means live in one place. And SpaceController reaches the user interface only through a weak SpaceControllerDelegate SpaceController.swift:119, implemented by AppDelegate; it never imports a view.

How the layers communicate

There is no Combine, no @Observable on the hot path, and no reactive graph. The mechanisms, in the order you will meet them:

DirectionMechanism
Keyboard → controller SpaceController is the KeyboardEventDelegate. The tap delivers a DebutKeyEvent enum value into one large switch.
Discovery → policy Assignable closures on the discovery service (onAppTerminated, onFrontmostAppChanged, and so on), attached by AppDelegate.
Controller → UI A weak delegate protocol with seven methods — including paired overloads of DidOpenOverlay and DidCloseOverlay that carry an OverlayPresentationContext — plus two escaping closures for the cases that did not justify a method.
Controller → keyboard Direct property write. The controller mirrors overlayVisible into the tap service so the tap can decide whether to consume an event without asking anyone.
Model → view Push. The delegate builds a whole new OverlayViewModel value and assigns it as the SwiftUI root view. There is no observation.
Why push instead of observation

OverlayViewModel is a plain Sendable struct whose stages property is computed on access. Rebuilding and reassigning it is a single diff for SwiftUI, and it makes overlay refreshes explicit and countable — which matters because the overlay's presentation latency is measured phase by phase (chapter 8). An observation graph would scatter those refreshes across the code and make them impossible to attribute.

The protocol seams

Two protocols carry essentially all of the untestable system surface, and every other type is written against them:

WindowService Services/WindowService.swift:107
Listing running apps and windows, classifying untrackable window IDs, capturing preview images, raising a window, activating an app, and checking Accessibility. Real implementation: AccessibilityWindowService. Double: MockWindowService.
KeyboardService Services/KeyboardService.swift
Starting and stopping the global tap and delivering DebutKeyEvents to a delegate. Real implementation: EventTapKeyboardService. Double: MockKeyboardService, which can synthesize any event synchronously.

A third category of seam is not a protocol but an injectable closure with a production default — for example the clock used for preview cache expiry, the launch-discovery delay (set to zero in tests to make discovery synchronous), and several Accessibility scan overrides documented as "production leaves this nil". This keeps the protocol surface small while still letting a test drive an otherwise unreachable branch.

Threading

The model is best described as "main thread by construction, with two deliberate exceptions".

  • AppDelegate is @MainActor. Everything it does is main-thread by isolation.
  • WindowDiscoveryService is @unchecked Sendable with plain unguarded dictionaries. Its safety argument is not locking but entry points: every way in — workspace notifications, Accessibility observer callbacks attached to the main run loop, and a process-exit dispatch source targeting the main queue — is already on the main thread.
  • Exception 1: the event tap. It runs on its own dedicated thread with its own run loop, because a tap that blocks is a tap the system disables. It hops to the main queue to deliver events, and its own session state is unguarded precisely because only that one thread touches it.
  • Exception 2: capture and image analysis. Screen captures run concurrently in a task group, and preview luminance analysis is pushed off the main queue to keep the render path free.
  • SpaceController is @unchecked Sendable rather than @MainActor, and uses MainActor.assumeIsolated at the three points where it touches the desktop surface SpaceController.swift:267, 648, 655.
The rule that shapes everything

No workspace or cross-process Accessibility call may happen inside the event-tap callback. Those calls block keyboard delivery and can cause the system to disable the tap outright. This is why the frontmost application's bundle ID is cached from activation notifications and why the tap's exclusion check is a plain set lookup.

Lifecycle hooks

applicationDidBecomeActive
Re-checks permissions, which is how returning from System Settings advances the onboarding state.
applicationShouldTerminateAfterLastWindowClosed
Returns false. Debut has no primary window; closing Settings must not quit it.
applicationWillTerminate AppDelegate.swift:346
Finalises any in-flight presentation traces, synchronously flushes the debounced state save, and gives telemetry at most half a second to drain before returning. The Info.plist disables both sudden and automatic termination, which is what makes this hook reliable enough to be the only save barrier.
Menu bar
An NSStatusItem with three items — Settings, Tutorial, Quit. Its visibility is a user setting.
